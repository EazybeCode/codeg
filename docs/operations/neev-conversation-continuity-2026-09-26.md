# Agent conversation continuity

## Problem

A follow-up such as “retry” received only the last 12 chat messages, each shortened to 600 characters. A stored 1,343-character request therefore ended midway through point 5; point 10 was at character 1,175. The earlier HTML (22,732,316 bytes) remained stored, but a fresh run staged only attachments on its current request.

## Change

Each private session or shared-chat run receives a staged `conversation.md` plus earlier linked uploads from that same conversation. The prompt contains brief orientation, labels excerpts, and points to the actual staged paths. Current uploads and historical files occupy separate directories; historical images are available as files rather than automatically resubmitted as image inputs.

History reads prove the current conversation ACL. Shared chats never receive the invoker’s private session history. Earlier uploads are reloaded through the existing authorized blob reader. Context files are temporary, consume no user attachment rows, and cannot overwrite configuration files. Staging errors fail the run rather than claiming missing files were supplied.

Transcript coverage is bounded at the newest 400 entries and 512 KiB, keeping each included entry intact and reporting omissions. Historical uploads use existing organization storage/count bounds rather than a new per-file size limit. Long file inventories are available through the context directory without overflowing command-line argument limits.

This does not persist files generated by an agent, introduce provider-native session resume, or add LLM summarization.
